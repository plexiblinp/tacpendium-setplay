# 2026-10-31 ux（設計）: KA が分からないまま 1 回で離脱する利用者への対策

- 状態: **設計の案**（実装していない）。文言・体験は開発者と詰めてから実装する（開発者 2026-10-31）。
- 種類: `ux`。利用者に見える仕様の変更なので、実装の前に開発者が決める（AGENTS §3）。

## 起きていること（開発者の分析）

KA に、実際のゲームの条件ではなさそうな切りの良い値（推測: 10・50・100 など）を入れ、1 回動かして離脱している節がある。

いまの画面（`web/src/components/ConditionsPanel.tsx`・`Guide.tsx`・`web/src/locales/ja.json`）:

- KA の欄は**空欄で始まる**（`initialForm` の `kaText: ""`）。欄の下の説明は「コンボの締めでダウンさせた後の有利フレーム（0〜100）」の 1 行だけ。
- **測り方**（トレーニングモードでフレーム表示 → コンボ後に棒立ちで有利フレームを見る）は、冒頭の「使い方」に書いてあるが、**最初は閉じている**（`<details>`）。
- 説明の「（0〜100）」が、範囲の端（0・100）や切りの良い値を誘っている可能性がある（推測）。
- KA 80 以上は計算が重く（`SLOW_KA_THRESHOLD = 80`）、現実に無い値では 0 件か、意味の薄い大量の結果になる（推測）。

**技ごとの KA はデータに無い**: moves DB の `onHit` はダウンを取る技では `null`（例: ケンの 2HK・236HK）。公開版 tacpendium でも `knockdown_advantage` は利用者のコンボの表（`migrations/000001_init_schema.up.sql` の 151 行）にしか無く、キャラのデータには無い。そのため「締めの技を選ぶと KA が入る」形は作れない（取込元は公開版だけ＝HANDOVER D2）。

## 案

### A. 欄の横の「これは何？」

- **押して開く形を勧める**（マウスを合わせて開く形は、スマホ〔タッチ〕では使えない。合わせても開く、を足すのは可）。
  - 実装: ボタン（`aria-expanded`）＋その下に開く説明の箱。キーボード（Tab → Enter）でも開く。Esc・もう一度押すと閉じる。
  - 外部のライブラリは要らない（React の状態だけ）。
- 中身の案（文言は詰める）:
  1. 何か: 「コンボの締めで相手をダウンさせたあと、相手が起き上がるまでに自分が先に動けるフレーム数」
  2. 測り方: 「トレーニングモードでフレーム表示をオン → コンボを当てたあと棒立ち → 表示される有利フレーム（+○○）の数字」
  3. 例: B の 1 例（「例: リュウの○○の後は ○○F」）
- 欄の下の「（0〜100）」は、誤りのときだけ出す形にする案もある（範囲の端を誘わないため。推測の効果）。

### B. お試しボタン（「例で試す」）

- 置き場所: KA の欄の近く（「これは何？」の説明の中にも同じボタン）。
- 押すと: 開発者が決めた 1 例（キャラ・KA・ほかの条件は既定）を欄に入れ、そのまま「提案を出す」と同じ計算をする。結果の上に「例の条件で計算しました（○○の後）。自分のコンボの KA を入れて試してください」と出す。
- 入れた条件は普段どおり URL にも入る（共有できる）。言語・表記は変えない。
- 例の値は `web/src/lib/constants.ts` に 1 か所で持つ。SF6 の調整で値が変わったら、開発者が直す（`data` の作業のときに確かめる項目に足す）。
  - 例の条件で結果が 0 件にならないことを、試験（実データの E2E）で守る。キャラのデータが変わって 0 件になったら CI が赤になる。
- ローカル版にも出す（通信はしない。計測も送らない＝いまと同じ）。

### D. 効果の計測

**beacon に「どう始めた実行か」を 1 列足す**（お試しの計測。開発者の要望）:

- `edge/beacon-layout.json` の `blobs` の末尾に `trigger`（順を変えない＝過去の点の読み方を守る）。値は `form`（「提案を出す」）・`share`（共有 URL を開いた自動計算）・`trial`（お試し）。過去の点は空文字（＝未計測。`form` と混ぜない＝AGENTS §8-7）。
- 共有 URL の自動計算と区別できるのは、お試し以外にも役に立つ（共有からの流入が分かる）。
- プライバシーポリシー: いまの文は「『提案を出す』を押したときの条件・結果・処理時間など」。`docs/maintenance.md`「ux」5 に従い、全ロケールに「（お試しの例か、共有のリンクからか、を含む）」を足し、`PRIVACY_LAST_UPDATED` を更新する。IP・個人に結び付く値は増えない。

**集計（`web/scripts/analytics/report.mjs`）に表を 3 つ足す**（画面は変わらない。開発者の手元だけ）:

1. KA の値の上位 20（切りの良い値〔10 の倍数〕の割合も）
2. 始め方（`trigger`）ごとの実行数
3. 推定利用者ごとの、1 日の実行回数の分布（1 回だけで終わった人の割合。SQL API は FROM の副問い合わせに対応＝cloudflare-docs の statements の FROM clause）
   - 限界: 推定利用者は日替わりのハッシュなので、日をまたいだ再訪は数えられない。抽出率（いま `config.json` の `beaconSampleRate` は 1）が 1 未満の日は、1 人の実行が欠けて「1 回だけ」が多く見える。

対策の前に 1〜2 週間分の値を取っておき、出した後と比べる。

## 動画・スライドについて（開発者の問い）

| 形 | 良い点 | 問題 |
|---|---|---|
| 文＋自作の図（SVG。「締め → ダウン → 起き上がり」の時間の帯に KA を示す） | 軽い。5 言語に訳せる（図の文字も i18n）。権利の問題が無い | 動きは伝わりにくい |
| 静止画（ゲームの画面の撮影） | 「どの数字を見るか」が一目で分かる | **ゲームの画面は Capcom の著作物**。載せてよいかは権利の判断（AGENTS §3 の 6）。言語ごとに画面が違う |
| 動画（自前で配る） | いちばん分かりやすい | 上と同じ権利の判断。容量（配信の上限 1 ファイル 25 MiB）。作る手間 |
| 動画（YouTube の埋め込み） | 容量の問題が無い | CSP（`frame-src` を開ける）、YouTube の cookie（HANDOVER §7.3 で cookie を使わない）、プライバシーポリシーの変更。**勧めない** |
| 外部の動画へのリンクだけ（開発者の動画・解説記事） | 画面は変わらない。権利は投稿先で済む | サイトの外へ出ていく |

**勧め**: まず **文＋自作の図** で A を作り、効果を D で見る。足りなければ、ゲームの画面を使うかどうか（権利の判断）を決めてから、静止画 1 枚か、外部の動画へのリンクを足す。
