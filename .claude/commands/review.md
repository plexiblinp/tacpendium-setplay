段階 **S$ARGUMENTS** の成果物をレビューする。**コードも docs も変更しない。書いてよいのは `docs/progress/S<n>-review.md` だけ。**

- 基準コミットが渡されなければ、`docs/progress/S<n>-report.md` の計画節に記録された開始コミットを使う。見つからなければ「基準不明」と書き、`git log` から推定した基準と根拠を書く。
- 前提として読む: `AGENTS.md`（§4 コーディング・§8 検証と報告）、HANDOVER §9 の自段階の行（完了条件）、`S<n>-report.md`。

## 観点
1. **完了条件への適合**: HANDOVER §9 の完了条件と、報告の計画節に挙げた項目が満たされているか。満たしていない項目が「判断」と書かれていないか（実装しなかったなら「逸脱」）。
2. **証拠**: 報告の「緑」に、コマンド・`EXIT=`・件数の逐語があるか。可能なら自分でもテストを回し、報告と一致するか確かめる（出力はファイルへ、`EXIT=` を出す）。
3. **テストが効いているか**: 新しいテストが、守る対象を消しても緑のままにならないか。単体の緑だけで配線（Go→WASM→TS、CLI→JSON→画面）を保証したことにしていないか。
4. **差分**: `git diff --stat <基準>` と `git diff <基準>` を読む。新規であるべきファイルから行が消えていないか、テストが黙って減っていないか。
5. **正しさ**: エンジン・絞り込みの挙動が本家（公開版 tacpendium の `internal/service/setplay/`。`bash scripts/fetch-upstream.sh` で `.upstream/tacpendium/` に取得）と食い違っていないか。打ち切りは並べ替えの後か。未計測／該当なし／false を同じ値に寄せていないか。
6. **文言**: i18n のキーが全ロケールにあるか。仕様を変えた箇所で、古い記述が docs・コメント・5 言語の文字列に残っていないか。
7. **禁止事項**: AGENTS.md §7（秘密情報、公式データの混入、combomgr を取込元にすること等）。

## 優先度
- **高**: 完了条件の未達、誤った結果を出すバグ、証拠の無い「緑」、テストが効いていない、**コードと食い違うコメント・docs**（テストは緑のままで読み手しか気づけないため）、禁止事項。
- **中**: 保守性・テストの不足・境界値の未確認。
- **低**: 命名・書式・好み。

## 報告の型（`docs/progress/S<n>-review.md`）
1. 要約（3〜5 行）
2. 完了条件への適合（項目ごとに 済／未／一部 と根拠）
3. 指摘（高・中・低ごとに: 場所 `path:line`・内容・なぜ問題か・直し方の案）
4. 良かった点
5. 自分で回したコマンドと結果（`EXIT=` と件数の逐語）

推測で書いたことは「推測:」と明示する。指摘が無い観点は「指摘なし（何を見たか）」と書く。
